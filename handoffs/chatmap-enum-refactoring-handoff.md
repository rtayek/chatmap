# Codex Handoff: Replace Closed-Set Strings with Enums in ChatMap

## Goal

Replace stringly typed values that represent closed conceptual sets with Java enums. Keep database values stable, keep display text independently changeable, and preserve tolerant reading of future or unknown values.

This is a focused type-safety refactoring. Do not redesign storage, providers, or the import identity policy in this pass.

## Current repository state

- Repository: `rtayek/chatmap`
- Review baseline: `master` at `2190100` (`Add domain package test coverage`)
- `Source` is already an enum with stable `dbValue` strings.
- `Chat.originatedBy` is still a `String` containing values such as `"IMPORTED"` and `"GENERATED"`.
- `Message.role` is still a `String`; common values are `"user"`, `"assistant"`, `"system"`, `"tool"`, and `"unknown"`.
- Backend IDs, provider IDs, external conversation IDs, model names, project names, tags, paths, URLs, titles, and hashes are open-ended identifiers and must remain strings.

## Design rule

Every closed-set enum should distinguish:

1. **Enum member** — stable identity used by Java logic.
2. **`dbValue`** — stable serialized value used by SQLite and exported machine-readable data. Once real data exists, changing this requires an explicit migration.
3. **`displayName`** — user-facing text. This may change without migrating the database.

Never persist `enum.name()` and never depend on `toString()` for storage.

Read persisted values through a tolerant `fromDbValue` method. An unrecognized or null value should map to `unknown`, allowing older ChatMap versions to open data written by newer versions.

## Enums to add

### `ChatOrigin`

Create `src/chatmap/domain/ChatOrigin.java`:

```java
package chatmap.domain;

/** Describes whether a chat was imported from a source or generated by ChatMap. */
public enum ChatOrigin {
    imported("IMPORTED", "Imported"),
    generated("GENERATED", "Generated"),
    unknown("UNKNOWN", "Unknown");

    private final String dbValue;
    private final String displayName;

    ChatOrigin(String dbValue, String displayName) {
        this.dbValue = dbValue;
        this.displayName = displayName;
    }

    public String dbValue() {
        return dbValue;
    }

    public String displayName() {
        return displayName;
    }

    public static ChatOrigin fromDbValue(String value) {
        for (ChatOrigin origin : values()) {
            if (origin.dbValue.equals(value)) {
                return origin;
            }
        }
        return unknown;
    }
}
```

The uppercase database strings are intentional: they preserve the values already present in existing databases.

## Boundary rule

Provider-specific DTOs and raw JSON parsing may temporarily retain strings because those strings come from an outside system. Convert them to domain enums before constructing `Message` or `Chat`.

For example:

```java
private static MessageRole normalizeRole(String providerRole) {
    if (providerRole == null) {
        return MessageRole.unknown;
    }
    return switch (providerRole.toLowerCase(java.util.Locale.ROOT)) {
        case "user", "human" -> MessageRole.user;
        case "assistant", "model", "gemini", "claude" -> MessageRole.assistant;
        case "system" -> MessageRole.system;
        case "tool" -> MessageRole.tool;
        default -> MessageRole.unknown;
    };
}
```

Do not use this exact mapping indiscriminately across all providers. Keep provider-specific mappings where their vocabularies differ.

## Values that must remain strings

Do not create enums for open-ended or user-extensible values:

- backend and provider IDs;
- model names;
- external conversation IDs;
- session IDs;
- paths, URLs, source URIs, and hashes;
- titles, project names, and tag names;
- free-form status or diagnostic text.

Existing enums such as `ImportService.Outcome` and `PromptProfile` are already appropriate. Do not add `dbValue` or `displayName` unless those enums actually cross a persistence or UI boundary.
